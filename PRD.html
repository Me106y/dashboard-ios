总体技术判断

算法对等、实现重写——不是把 Kotlin 翻译成 Swift

上游把 30 多个渲染阶段用「构造顺序」隐式串联，几乎每个阶段各占一张全分辨率纹理，还带着 6 个 OpenCV 平行实现与若干不可达调试管线。iOS 版用 Metal + Core ML 重写同一条算法链，同时不继承这些欠债：零第三方二进制依赖，只有 Swift / SwiftUI / Metal / AVFoundation / Core ML。

总体技术判断

四条支撑整个方案的判断，每条都来自对上游源码的实际阅读。

后端

渲染换 Metal

上游 28 个着色器共 727 行，多为简单采样与算术，逐字翻译成 MSL 的成本有界；换来 Apple 唯一有长期支持的实时渲染路径。

模型

分割转 Core ML

线上跑的其实是 PaddleSeg 官方 PP-HumanSegV2 portrait（MobileNetV3 骨干），不是 README 宣传的自研模型——意味着 ONNX 转换路径成熟，且可吃 ANE 加速。

依赖

彻底移除 OpenCV

OpenCV 在启用管线里只剩 3 处用途：霍夫直线、5×5 膨胀、单应求解。全部可用 Swift + Metal + simd 替代，不值得背一个几十 MB 的原生库。

顺序

先跑通模型

P0 的唯一目标是把 PP-HumanSegV2 portrait 在 Core ML 上跑出合理 mask；在此之前不写任何业务代码。

关键发现

以下 7 条均为阅读源码时确认，直接决定了 iOS 版的设计取舍。

01

线上模型与宣传不符

已确认

model/ 目录里是自研的 MobileSegV2 + RepViT + EASPP，但 App 打包并实际加载的是 PaddleSeg 官方 humansegv2 系列。证据：model.pdiparams.info 中参数名为 net.backbone.blocks.N.{expand_conv,bottleneck_conv,linear_conv}（MobileNetV3 倒残差）与 net.ppseg_head.last_conv.depthwise_conv / piontwise_conv（PPHumanSegHead / ASPP）。README 的「1.97M 参数 / EASPP / mIoU 0.9096」属于训练代码口径。

02

管线依赖是隐式的

架构欠债

Pipeline.draw() 就是 stages.forEach { it.performUpdate() }，数据依赖全靠「谁先被 new」。移植 30 多个阶段时这是 bug 温床 → 决策 D13 强制显式声明输入输出。

03

纹理开销高

架构欠债

几乎每个阶段各分配一张全分辨率纹理（1080p RGBA ≈ 8 MB/张）→ 决策 D13 引入纹理池按引用计数复用。

04

手动拖角点是盲拖

UX 缺陷

DraggablePointsStage 只持有 4 个点，不绘制任何手柄；corner_shader / line_shader 存在，但只用在未接入主流程的调试组合里 → iOS 版复用这两个着色器做可视手柄。

05

手势有副作用

UX 缺陷

ACTION_DOWN 会触发 DrawPipelineStage.next() 切换显示阶段，而拖动角点必然先经过 ACTION_DOWN——每次伸手拖角点，画面都会跳到下一个中间阶段 → 决策 D14 修正手势语义。

06

OpenCV 大材小用 + 死代码

可移除

主路径的 OpenCV 调用只有 Imgproc.HoughLines、Imgproc.dilate、getPerspectiveTransform 三处；另有 6 个 OpenCV 平行实现（binarization / canny / grayscale / gaussian / sobel / cornerDetection）与 GLSL 版本重复且不可达 → 决策 D5 完全移除。

07

朝向写死

可移除

segment_preprocess_shader.glsl 用 vec2(1.0 - uv.y, uv.x) 把画面转向分割网络，注释明确写着「hardcoded for right handed landscape orientation，TODO 处理手机方向」→ 决策 D8 朝向参数化。

架构决策 D1–D14

全部决策已与需求方逐条确认，构成本次移植的设计契约。

#决策点结论理由摘要
D1移植范围全流程对等（五模块全做）卖点是「去遮挡 + 高保真输出」，砍掉透视与增强后演示价值大打折扣
D2图形后端Metal（MTKView + CVMetalTextureCache）OpenGL ES 自 iOS 12 起废弃 8 年；28 个着色器共 727 行，翻译成本有界
D3分割推理Core ML，先跑通 PP-HumanSegV2 portraitANE 硬件加速、零额外运行时；模型是官方结构，转换路径成熟
D4转换验收视觉验收（数值比对降级为备用诊断）先看效果，不先花成本搭数值比对链路
D5CV 方案不用 OpenCV，霍夫/四边形/单应用 Swift + simd主路径只剩 3 处用途，不值得引入几十 MB 原生库
D6相机管线AVCaptureSession + AVCaptureVideoDataOutput，32BGRACVPixelBuffer 经 CVMetalTextureCache 零拷贝成 MTLTexture，无需色彩转换着色器
D7采集规格1920×1080 @ 30fps，不预先降分辨率分割网络输入仅 256×144；分辨率不足时再谈降级
D8朝向策略v1 锁横屏，朝向作 uniform 传入避开「传感器方向 / 预览方向 / 分割输入 / 显示」四者互相打架
D9帧源抽象输入藏在 FrameSource 协议后CameraFrameSource / StillImageFrameSource；静态图验证不改管线代码
D10App 外壳SwiftUI 壳 + UIKit MTKView 画布触摸留在 UIKit，touchesBegan/Moved 与 onTouchEvent 一对一映射
D11最低系统iOS 17.0覆盖 A12+（均有 ANE），可用现代 SwiftUI，无需老系统分支
D12工程生成手写 .xcodeproj + 同步文件夹零额外工具；新增 .swift/.metal 无需改工程文件
D13管线架构混合式：顺序列表 + 显式输入输出 + 纹理池 + 推理解耦兼顾移植速度（一个着色器=一个阶段）与长期可维护性
D14交互模型显式控制条 + 修正手势语义单击切调试视图、拖动只拖角点；消除发现 05 的副作用

P0 转换实录

P0 是本次移植技术风险最高的一步。过程与结论记录在此，避免重复踩坑。

P0 结论

模型转换链路已打通并逐像素验证

最终链路：pdmodel+pdiparams →（paddle2onnx 1.3.1 / paddlepaddle 2.6.2 + 图修复）→ ONNX [1,3,144,256] f32 → [1,144,256] i32 →（onnx2torch → torch.jit.trace）→ TorchScript →（coremltools 8.1，mlProgram / iOS 17+ / FLOAT16）→ .mlpackage 图像输入 256×144 RGB，输出 mask [1,144,256] INT32，1.9 MB。

R1

六个实际卡点

已全部解决
#卡点根因解法
1ONNX 加载失败ASPP 的 AdaptiveAvgPool 在动态输入下无法推导 kernel，导出 kernel_shape=[-1,-1]钉死输入形状，按 Paddle 语义换算成等价固定核
2Paddle 3.x 读不了模型load_inference_model 走 PIR 分支，UnicodeDecodeError锁定 paddlepaddle 2.6.2
3没有 ONNX→Core ML 通道coremltools 自 7.0 移除 ONNX 前端；7.2 在本机原生库还加载失败走官方路线：ONNX → PyTorch → TorchScript → Core ML
4onnx2torch KeyErrorpaddle2onnx 把 414 个权重内联成 Constant 节点常量提升：Constant → initializer
5SAME_UPPER 不支持onnx2torch 未实现自动填充形状已固定，把 19 个 SAME_* 展开成显式 pads；形状推导必须开 data_prop=True
6Core ML 图像预处理报错scale 需标量、bias 需三元组（pass 内部会 reshape 成 [1,3,1,1]）按各自要求传参
